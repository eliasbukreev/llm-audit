# Описание архитектуры программного обеспечения (п. 5.6 ГОСТ Р 56939-2024)

## Цели

- **Основная цель**: подготовить описание архитектуры ПО, требования к принципам проектирования и критерии уточнения архитектуры для анализируемого проекта, формально удовлетворяющие пункту 5.6 ГОСТ Р 56939-2024.
- **Зависимость**: задача выполняется **после** завершения анализа по п. 5.1. Исходные данные берутся из `results/{repo-name}/Анализ текущего состояния процессов разработки безопасного ПО.md`. Рекомендуется использовать `results/{repo-name}/Регламент управления требованиями безопасности ПО.md` (п. 5.3) для привязки требований безопасности.
- **Формат**: Markdown-файл `results/{repo-name}/Описание архитектуры ПО.md`, где `{repo-name}` — имя репозитория из результата 5.1.
- **Файловая структура**: план — `docs/plans/`, шаблон — `docs/templates/`, ГОСТ — `docs/standarts/`, выход — `results/`.

## 1. Подготовка

### 1.1. Определить имя проекта и пути к результатам

- Имя репозитория `{repo-name}` известно из контекста. Прочитай `results/{repo-name}/Анализ текущего состояния процессов разработки безопасного ПО.md`. При наличии — `results/{repo-name}/Регламент управления требованиями безопасности ПО.md`.

### 1.2. Изучить требования ГОСТ 5.6

- Прочитай раздел 5.6 «Разработка, уточнение и анализ архитектуры программного обеспечения» из `docs/standarts/ГОСТ Р 56939— 2024.md`.
- Зафиксируй структуру по 5.6.3.1 (принципы проектирования), 5.6.3.2 (описание архитектуры), 5.6.3.3 (критерии уточнения).

### 1.3. Ознакомиться с шаблоном

- Прочитай `docs/templates/Описание архитектуры ПО (п.5.6 ГОСТ).md`.

## 2. Извлечение данных из результата 5.1

Из результата 5.1 извлеки:

- **Название проекта**, описание системы и среды (разделы 1–2).
- **Архитектуру** — компоненты, модули, стек технологий, взаимодействия (раздел 2–3).
- **Оценку процесса 5.6** из таблицы 4.1 и план развития для 5.6 из раздела 5.

## 3. Формирование требований к принципам проектирования (по 5.6.3.1)

Определи и опиши принятые подходы и принципы проектирования с точки зрения безопасности, например:
- инкапсуляция, разделение ответственности;
- «нулевое доверие», протоколирование событий, резервное копирование;
- формирование перечня недопустимых событий;
- приоритетное использование языков с безопасной моделью памяти и т.п.

Адаптировать под стек технологий проекта.

## 4. Формирование описания архитектуры (по 5.6.3.2)

Описание должно включать:

1. **Назначение ПО и сценарии использования** — для чего предназначено, основные use-cases.
2. **Описание среды функционирования** — ОС, СУБД, сеть, облако и т.п.
3. **Ограничения и указания по применению** — ограничения по масштабированию, лицензиям, зависимостям.
4. **Проект на уровне подсистем (модулей)** — назначение, структура, особенности реализации, языки программирования, взаимодействие (интерфейсы, порты, протоколы).

## 5. Формирование критериев уточнения архитектуры (по 5.6.3.3)

Определи:
- **Периодичность пересмотра** архитектуры (например, раз в квартал).
- **События**, при наступлении которых необходимо уточнять архитектуру (новый модуль, смена технологий, выявление уязвимости, значительный рост нагрузки и т.п.).

## 6. Создание итогового документа

- Создать файл `results/{repo-name}/Описание архитектуры ПО.md`.
- Заполнить по структуре шаблона, подставив данные из п. 2–5.
- Сохранить в стандартной Markdown-разметке.

## 7. Проверка

- Требования к принципам (5.6.3.1), описание (5.6.3.2), критерии уточнения (5.6.3.3) присутствуют.
- Описание опирается на результат 5.1 и отражает фактическую архитектуру проекта.
