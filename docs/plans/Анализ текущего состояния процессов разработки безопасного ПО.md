# Анализ текущего состояния процессов разработки безопасного ПО

## Цели

- **Основная цель**: подготовить структурированный документ "Анализ текущего состояния процессов разработки безопасного ПО" для **любого** анализируемого репозитория, который формально удовлетворяет пункту 5.1.3.1 ГОСТ Р 56939-2024.
- **Формат**: Markdown-файл с названием `security-analysis-{repo-name}.md` в папке `results/`, со структурой, удобной для конвертации в DOCX.
- **Универсальность**: план применим к любому репозиторию. Пример результата для одного проекта (ОПРОСНИК) — `docs/templates/Анализ текущего состояния процессов разработки безопасного ПО.md`; при анализе другого репозитория подставляй его фактическое название вместо "ОПРОСНИК" во всех разделах документа.
- **Файловая структура** (MCP server-filesystem): план — `docs/plans/`, шаблон примера — `docs/templates/`, ГОСТ — `docs/standarts/`, итоговые отчёты — `results/`.

## 3. Сбор фактической информации по проекту

### 3.1. Изучение структуры и архитектуры проекта

- **3.1.1. Найти и проанализировать README файлы**:
  - Используй MCP filesystem (list_dir, read_file) для поиска `README.md`, `README.txt`, `README` на всех уровнях
  - Прочитай содержимое найденных README
  - Извлеки информацию о: назначении проекта, стеке технологий, архитектуре, зависимостях, способах установки и запуска
- **3.1.2. Определить тип проекта**:
  - По расширениям файлов определи основной язык/фреймворк:
    - Python: `requirements.txt`, `setup.py`, `pyproject.toml`, `Pipfile`, `*.py`
    - JavaScript/TypeScript: `package.json`, `package-lock.json`, `yarn.lock`, `*.js`, `*.ts`, `*.jsx`, `*.tsx`
    - Java: `pom.xml`, `build.gradle`, `*.java`
    - Go: `go.mod`, `go.sum`, `*.go`
    - Ruby: `Gemfile`, `Gemfile.lock`, `*.rb`
    - PHP: `composer.json`, `composer.lock`, `*.php`
    - C#/.NET: `*.csproj`, `*.sln`, `packages.config`
    - Rust: `Cargo.toml`, `Cargo.lock`, `*.rs`
    - Мультиязычные проекты: определи основные компоненты
- **3.1.3. Проанализировать структуру директорий**:
  - Используй list_dir (MCP filesystem) с различными глубинами для понимания организации проекта
  - Определи наличие типовых директорий: `src/`, `lib/`, `app/`, `backend/`, `frontend/`, `api/`, `web/`, `mobile/`, `docs/`, `tests/`, `scripts/`, `docker/`, `config/`, `deploy/`, `infra/`, `kubernetes/`, `terraform/`
- **3.1.4. Найти конфигурационные файлы инфраструктуры**:
  - Docker: `Dockerfile`, `docker-compose*.yml`, `docker-compose*.yaml`, `*.dockerfile`
  - CI/CD: `.github/workflows/*.yml`, `.gitlab-ci.yml`, `Jenkinsfile`, `.circleci/config.yml`, `.travis.yml`, `azure-pipelines.yml`
  - Оркестрация: `kubernetes/*.yaml`, `helm/`, `terraform/*.tf`, `cloudformation/*`
  - Make: `Makefile`, `makefile`
- **3.1.5. Найти файлы с зависимостями для анализа безопасности**:
  - Python: `requirements.txt`, `Pipfile`, `pyproject.toml`, `poetry.lock`
  - Node.js: `package.json`, `package-lock.json`, `yarn.lock`, `npm-shrinkwrap.json`
  - Java: `pom.xml`, `build.gradle`
  - Go: `go.mod`, `go.sum`
  - Ruby: `Gemfile`, `Gemfile.lock`
  - PHP: `composer.json`, `composer.lock`
  - Rust: `Cargo.toml`, `Cargo.lock`
  - .NET: `packages.config`, `*.csproj`

### 3.2. Анализ процесса разработки

- **3.2.1. Система контроля версий**:
  - Определи наличие `.git` директории (почти всегда есть)
  - Найди `.gitignore` и проанализируй, что исключено из репозитория (секреты, конфиги, бинарные файлы)
  - По возможности (если есть доступ к истории) оцени наличие веток, тегов, но для базового анализа достаточно факта использования Git
- **3.2.2. Процесс внесения изменений**:
  - Ищи наличие pull request/merge request шаблонов: `.github/PULL_REQUEST_TEMPLATE.md`, `.gitlab/merge_request_templates/`
  - Найди файлы, регламентирующие процесс: `CONTRIBUTING.md`, `docs/contributing.md`
  - Оцени наличие код-ревью по косвенным признакам: шаблоны PR, требования к описанию изменений
- **3.2.3. Документация процесса**:
  - Опиши на основе найденного: "процесс разработки документирован минимально/частично/полностью", "есть/отсутствуют руководства для контрибьюторов"

### 3.3. Анализ CI/CD и автоматизации

- **3.3.1. Найти конфигурации CI/CD** (из п.3.1.4)
- **3.3.2. Проанализировать найденные конфигурации**:
  - Какие шаги автоматизированы (сборка, тесты, линтеры, статический анализ, деплой)
  - Запускаются ли тесты автоматически при пушах/PR
  - Есть ли интеграция с инструментами безопасности
- **3.3.3. Сборка и артефакты**:
  - Найди `Dockerfile`(ы) и проанализируй, на чем основаны образы (официальные образы, легковесные дистрибутивы)
  - Оцени, используются ли многоступенчатые сборки (multi-stage) для уменьшения размера и поверхности атаки
  - Проверь, собираются ли артефакты (бинарные файлы, пакеты) и где хранятся

### 3.4. Анализ тестирования

- **3.4.1. Найти тестовые директории и файлы**:
  - Поиск по паттернам: `test_*.py`, `*_test.py`, `*_test.go`, `*_test.js`, `*_spec.js`, `*_spec.rb`, `__tests__/`, `tests/`, `test/`, `spec/`
- **3.4.2. Определить типы тестов**:
  - Модульные тесты (unit) — обычно в тех же директориях, что и код, или в `tests/unit`
  - Интеграционные тесты — в `tests/integration`, `tests/api`
  - E2E тесты — `cypress/`, `playwright/`, `selenium/`
- **3.4.3. Найти конфигурации тестовых фреймворков**:
  - Python: `pytest.ini`, `setup.cfg` (секция pytest), `.coveragerc`
  - JavaScript: `jest.config.js`, `karma.conf.js`, `cypress.json`, `playwright.config.ts`
  - Другие языки: соответствующие конфиги
- **3.4.4. Оценить покрытие кода тестами**:
  - Ищи файлы с отчетами о покрытии: `coverage.xml`, `.coverage`, `lcov.info`, `coverage/`
  - Проверь, упоминается ли покрытие в README или CI/CD конфигах

### 3.5. Анализ безопасности

- **3.5.1. Инструменты статического анализа (SAST)**:
  - Поиск конфигурационных файлов популярных инструментов:
    - Python: `bandit`, `prospector`, `pylint-plugins`, `flake8-bandit`
    - JavaScript: `eslint` (с плагинами безопасности), `sonarjs`
    - Java: `findbugs`, `spotbugs`, `pmd`, `checkstyle`
    - Go: `gosec`, `staticcheck`
    - Общие: `sonar-project.properties`, `.snyk`, `codeql-config.yml`
  - Проверь, запускаются ли эти инструменты в CI/CD
- **3.5.2. Анализ зависимостей (SCA)**:
  - Найди файлы зависимостей (из п.3.1.5)
  - Проверь наличие лок-файлов (`package-lock.json`, `yarn.lock`, `poetry.lock`, `Pipfile.lock`) — признак фиксации версий
  - Ищи файлы конфигурации для сканирования уязвимостей: `.nsprc` (Node Security), `.snyk`, `owasp-dependency-check` конфиги
  - Проверь, есть ли в CI шаги для проверки уязвимостей зависимостей
- **3.5.3. Динамический анализ (DAST)**:
  - Обычно редкость в открытых репозиториях, но проверь наличие упоминаний в CI/CD или документации
- **3.5.4. Управление уязвимостями**:
  - Поиск файлов, связанных с отчетностью по безопасности: `SECURITY.md`, `SECURITY`, `docs/security.md`
  - Проверь, есть ли процесс оповещения об уязвимостях (в SECURITY.md обычно указан контакт)
  - Оцени формальность процесса: есть/отсутствует

### 3.6. Анализ управления секретами

- **3.6.1. Найти файлы с конфигурацией окружения**:
  - Поиск: `.env`, `.env.example`, `.env.sample`, `.env.dist`, `config/`, `settings/`, `configuration/`
  - Проанализируй `.env.example` или аналоги — какие переменные окружения требуются, есть ли среди них чувствительные (пароли, ключи API, токены)
- **3.6.2. Проверить практики работы с секретами**:
  - Проверь `.gitignore` — исключены ли `.env`, `secrets/`, `config/secrets.yml` и подобные
  - Найди, используются ли секреты в CI/CD (обычно через `secrets.` или `variables`)
  - Оцени, используются ли специализированные инструменты: `hashicorp-vault`, `aws-secrets-manager`, `azure-key-vault` (по упоминаниям в коде или конфигах)
- **3.6.3. Поиск утечек секретов в истории** (если доступна):
  - Обрати внимание на наличие явных паролей или ключей в файлах конфигурации (но это продвинутый уровень)

### 3.7. Анализ сопровождения и поддержки

- **3.7.1. Обновление зависимостей**:
  - Проверь даты изменений в файлах зависимостей (`package.json`, `requirements.txt` и т.д.)

- **3.7.4. Мониторинг и логирование**:
  - Поиск упоминаний инструментов мониторинга в конфигах: `prometheus`, `grafana`, `datadog`, `newrelic`, `sentry`
