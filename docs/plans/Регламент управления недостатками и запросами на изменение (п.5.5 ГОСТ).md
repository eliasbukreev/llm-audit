# Регламент управления недостатками и запросами на изменение ПО (п. 5.5 ГОСТ Р 56939-2024)

## Цели

- **Основная цель**: подготовить регламенты управления недостатками ПО и запросами на изменение для анализируемого проекта, формально удовлетворяющие пункту 5.5 ГОСТ Р 56939-2024.
- **Зависимость**: задача выполняется **после** завершения анализа по п. 5.1. Исходные данные берутся из `results/{repo-name}/Анализ текущего состояния процессов разработки безопасного ПО.md`.
- **Формат**: Markdown-файл `results/{repo-name}/Регламент управления недостатками и запросами на изменение ПО.md`, где `{repo-name}` — имя репозитория из результата 5.1.
- **Файловая структура**: план — `docs/plans/`, шаблон — `docs/templates/`, ГОСТ — `docs/standarts/`, выход — `results/`.

## 1. Подготовка

### 1.1. Определить имя проекта и путь к результату 5.1

- Имя репозитория `{repo-name}` известно из контекста. Прочитай `results/{repo-name}/Анализ текущего состояния процессов разработки безопасного ПО.md`.

### 1.2. Изучить требования ГОСТ 5.5

- Прочитай раздел 5.5 «Управление недостатками и запросами на изменение программного обеспечения» из `docs/standarts/ГОСТ Р 56939— 2024.md`.
- Зафиксируй структуру регламентов по 5.5.3.1 (недостатки) и 5.5.3.2 (запросы на изменение), а также поля артефактов по 5.5.3.3 и 5.5.3.4.

### 1.3. Ознакомиться с шаблоном

- Прочитай `docs/templates/Регламент управления недостатками и запросами на изменение (п.5.5 ГОСТ).md`.

## 2. Извлечение данных из результата 5.1

Из результата 5.1 извлеки:

- **Название проекта**, описание процессов разработки (разделы 1–3).
- **Используемые средства**: Git, issue-трекер, системы управления задачами (из раздела 3).
- **Оценку процесса 5.5** из таблицы 4.1 и план развития для 5.5 из раздела 5.

## 3. Формирование регламента управления недостатками (по 5.5.3.1)

Регламент должен содержать:

1. **Порядок идентификации недостатков ПО** — как выявляются и регистрируются недостатки.
2. **Порядок управления недостатками** — действия при выявлении, устранении, тестировании, принятии решения о закрытии недостатка.

Конкретизировать для проекта с учётом используемых средств (GitHub Issues, GitLab, Jira и т.п.).

## 4. Формирование регламента управления запросами на изменение (по 5.5.3.2)

Регламент должен содержать:

1. **Порядок идентификации запросов на изменение ПО** — как регистрируются предложения о добавлении, модификации, удалении элементов ПО.
2. **Порядок управления запросами** — действия при осуществлении запроса, тестировании, принятии решения о закрытии.

## 5. Шаблоны артефактов (5.5.3.3, 5.5.3.4)

Включить в документ шаблоны/таблицы для фиксации:
- **Недостатки** (5.5.3.3): идентификатор, описание, версия ПО, приоритет, статус.
- **Запросы на изменение** (5.5.3.4): идентификатор, характеристика, версия ПО, приоритет, статус.

## 6. Создание итогового документа

- Создать файл `results/{repo-name}/Регламент управления недостатками и запросами на изменение ПО.md`.
- Заполнить по структуре шаблона, подставив данные из п. 2–5.
- Сохранить в стандартной Markdown-разметке.

## 7. Проверка

- Регламент по недостаткам (5.5.3.1) и по запросам (5.5.3.2) содержат все требуемые разделы.
- Шаблоны артефактов (5.5.3.3, 5.5.3.4) включены.
- Документ опирается на результат 5.1.
