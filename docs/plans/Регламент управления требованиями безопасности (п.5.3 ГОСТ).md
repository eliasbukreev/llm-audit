# Регламент управления требованиями безопасности ПО (п. 5.3 ГОСТ Р 56939-2024)

## Цели

- **Основная цель**: подготовить регламент управления требованиями безопасности ПО для анализируемого проекта, формально удовлетворяющий пункту 5.3 ГОСТ Р 56939-2024.
- **Зависимость**: задача выполняется **после** завершения анализа по п. 5.1. Исходные данные берутся из `results/{repo-name}/Анализ текущего состояния процессов разработки безопасного ПО.md`.
- **Формат**: Markdown-файл `results/{repo-name}/Регламент управления требованиями безопасности ПО.md`, где `{repo-name}` — имя репозитория из результата 5.1.
- **Файловая структура**: план — `docs/plans/`, шаблон — `docs/templates/`, ГОСТ — `docs/standarts/`, выход — `results/`.

## 1. Подготовка

### 1.1. Определить имя проекта и путь к результату 5.1

- Имя репозитория `{repo-name}` известно из контекста (задача 5.3 запускается после 5.1 с тем же repo-name). Либо найди в `results/` подпапку с именем репозитория.
- Прочитай содержимое `results/{repo-name}/Анализ текущего состояния процессов разработки безопасного ПО.md`.

### 1.2. Изучить требования ГОСТ 5.3

- Прочитай раздел 5.3 «Формирование и предъявление требований безопасности» из `docs/standarts/ГОСТ Р 56939— 2024.md`.
- Зафиксируй структуру регламента по 5.3.3.1 и набор требований по 5.3.3.2.

### 1.3. Ознакомиться с шаблоном

- Прочитай `docs/templates/Регламент управления требованиями безопасности (п.5.3 ГОСТ).md`.

## 2. Извлечение данных из результата 5.1

Из `results/{repo-name}/Анализ текущего состояния процессов разработки безопасного ПО.md` извлеки:

- **Название проекта** — из раздела 1 (Введение).
- **Описание системы** — кратко из раздела 2.
- **Таблицу 4.1** (оценка по 25 процессам) — процессы с оценкой «частично» или «не соответствует» станут основой для первоначального набора требований безопасности.
- **План развития (раздел 5)** — «Ключевые меры по развитию» для процессов 5.3 и смежных процессов.

## 3. Формирование регламента (по 5.3.3.1)

Регламент должен содержать:

1. **Порядок предъявления требований безопасности ПО** — кто и как формулирует, кто утверждает.
2. **Порядок предоставления требований безопасности ПО исполнителям** — как требования доводятся до разработчиков/исполнителей.
3. **Порядок отслеживания** процесса предоставления, получения и выполнения требований (жизненный цикл требований, учёт статусов).
4. **Критерии пересмотра требований** — периодически (например, раз в квартал) и при наступлении определённых событий (релиз, выявление уязвимости, смена архитектуры и т.п.).

Описание должно быть конкретизировано для проекта `{repo-name}` с учётом его архитектуры и процессов (из результата 5.1).

## 4. Формирование набора требований безопасности (по 5.3.3.2)

На основе таблицы 4.1 и плана развития из 5.1 сформируй **первоначальный набор требований** по ГОСТ 5.3.3.2. Каждое требование должно содержать:

- идентификатор требования;
- формулировка;
- дата предъявления;
- приоритет/важность;
- предполагаемые сроки реализации;
- сведения о сотрудниках/подразделениях (предъявитель, исполнитель) — можно оставить как заглушки «будут уточнены».

Используй процессы с оценкой «частично» или «не соответствует» из результата 5.1 как источник формулировок требований.

## 5. Создание итогового документа

- **5.1.** Создать файл `results/{repo-name}/Регламент управления требованиями безопасности ПО.md` (папку `results/{repo-name}/` создать при необходимости).
- **5.2.** Заполнить документ по структуре шаблона, подставив данные из п. 2–4.
- **5.3.** Сохранить в стандартной Markdown-разметке для конвертации в DOCX.

## 6. Проверка

- Все разделы по 5.3.3.1 присутствуют.
- Набор требований содержит все поля по 5.3.3.2.
- Документ опирается на результат 5.1 и не противоречит ему.
